# PRD: 🧠 The Brain — Agent Swarm with Live Diagnostics

> **Module:** The Brain (Agent Orchestration)
> **Version:** 1.0
> **Last Updated:** 2026-04-26
> **Status:** Draft
> **Parent PRD:** [PRD_main_v0.0.md](./PRD_main_v0.0.md) — Section 4.4

---

## 1. Purpose

This PRD defines the detailed design of **The Brain** — the LangGraph-based agent swarm that performs incident analysis. It extends the architecture defined in `PRD_main_v0.0.md` Section 4.4 by augmenting the OS Engineer and Cloud Engineer agents with the ability to **execute read-only diagnostic commands** against the tenant's infrastructure in real time.

The main PRD establishes the graph topology:

```
Router → [OS Agent | Cloud Agent] (sequential) → Security Review (mandatory) → Output
```

This PRD preserves that topology exactly, but adds a **tool-use loop** inside each specialist agent: in addition to RAG retrieval, agents can now formulate and execute shell commands (Linux for OS, CLI for Cloud) to gather live data before reasoning.

---

## 2. Problem This Solves

The current architecture (PRD_main Section 4.4) relies entirely on:
1. The alert payload itself
2. RAG-retrieved historical context (ADRs, past incidents, runbooks, infra inventory)

This is powerful for pattern-matching against known issues, but **insufficient for novel or ambiguous incidents** where:
- The alert lacks detail (e.g., "High CPU" with no process-level breakdown)
- Historical context has no similar past incident
- The root cause requires live system state to diagnose (e.g., is the disk *actually* full right now? Which process is consuming memory?)

**Live diagnostic commands close this gap.** The agents can now autonomously decide when they need more data and fetch it directly from the tenant's infrastructure — all within the read-only constraint.

---

## 3. Alignment with Main PRD Section 4.4

This module **does not change** the graph topology or flow defined in Section 4.4:

| Section 4.4 Concept | This PRD's Treatment |
|---|---|
| Router → OS/Cloud → Security Review | **Unchanged.** Same graph, same sequential flow. |
| RAG retrieval (steps 1-5 per agent) | **Preserved.** RAG still executes first. Command execution is an additional step *after* RAG. |
| Mandatory Security Review with RAG grounding | **Unchanged.** Security Review now also validates the commands that were executed (audit trail). |
| STM/LTM memory model | **Extended.** Command outputs are stored in STM for session context. Successful diagnostics are embedded into LTM for future retrieval. |

| Read-only mode (v1) | **Enforced.** Only read-only commands are allowed. Enforced via allowlists. |

## 4. Agent Tool Architecture

### 4.1 The Tool-Use Loop

Each specialist agent (OS Engineer, Cloud Engineer) now operates in a **ReAct (Reason + Act) loop** powered by LangGraph's native tool-calling support:

```
┌─────────────────────────────────────────────────────────────────┐
│                    SPECIALIST AGENT (OS / Cloud)                 │
│                                                                 │
│  1. Receive alert/query + Router classification                 │
│          │                                                       │
│          ▼                                                       │
│  2. RAG Retrieval (unchanged from Section 4.4)                  │
│     • Embed query → sqlite-vec search → retrieve context        │
│          │                                                       │
│          ▼                                                       │
│  3. LLM Reasoning (iteration 1)                                │
│     • Analyze alert + RAG context                               │
│     • Decision: Do I have enough data to diagnose?              │
│          │                                                       │
│          ├──── YES → Produce final analysis → exit loop          │
│          │                                                       │
│          └──── NO → Formulate diagnostic command(s)             │
│                    │                                             │
│                    ▼                                             │
│  4. Command Execution (via The Hands)                           │
│     • Validate command against allowlist                        │
│     • Execute in sandboxed environment                          │
│     • Capture stdout/stderr                                     │
│     • Store output in STM                                       │
│          │                                                       │
│          ▼                                                       │
│  5. LLM Reasoning (iteration 2...N)                             │
│     • Analyze alert + RAG context + command outputs             │
│     • Decision: Do I have enough data now?                      │
│          │                                                       │
│          ├──── YES → Produce final analysis → exit loop          │
│          └──── NO → Formulate more commands (up to max_iter)    │
│                                                                 │
│  Max iterations: 5 (configurable)                               │
│  If max reached: produce best-effort analysis with available    │
│  data + flag that further investigation is needed               │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 Key Design Principles

1. **RAG-first.** Agents always consult long-term memory before executing any commands. If RAG provides sufficient context (e.g., identical past incident with known root cause), no commands are executed.
2. **Minimum-commands.** The LLM decides whether a command is needed — it is not automatic. This minimizes unnecessary load on tenant infrastructure.
3. **Read-only enforced.** Commands are validated against strict allowlists before execution. Any command not on the allowlist is rejected.
4. **Bounded iteration.** The ReAct loop is capped at a configurable maximum (default: 5 iterations) to prevent runaway execution.
5. **Full audit trail.** Every command executed, its output, and the agent's reasoning for executing it are logged in STM and passed to the Security Review.

## 5. OS Engineer Agent — Command Toolkit

### 5.1 Allowed Commands (Read-Only)

The OS Engineer Agent can execute these commands against the tenant's target Linux host via SSH:

| Category | Commands | Purpose |
|---|---|---|
| **System** | `uname -a`, `uptime`, `hostnamectl`, `timedatectl` | System identity and uptime |
| **CPU** | `top -bn1 -o %CPU`, `mpstat`, `pidstat`, `cat /proc/loadavg` | CPU diagnostics, per-process breakdown |
| **Memory** | `free -mh`, `vmstat`, `cat /proc/meminfo`, `slabtop -o` | Memory usage, swap, slab cache |
| **Disk** | `df -hT`, `du -sh /var/log/*`, `lsblk`, `blkid`, `cat /proc/mounts`, `iostat` | Disk usage, mount points, I/O stats |
| **Processes** | `ps aux --sort=-%mem`, `ps aux --sort=-%cpu`, `pstree -p` | Process listing, resource consumers |
| **Network** | `ss -tulnp`, `ip addr`, `ip route`, `cat /etc/resolv.conf`, `iptables -L -n -v` | Listening ports, routes, DNS, firewall |
| **Logs** | `journalctl -u <service> --no-pager -n 100`, `dmesg --level=err,warn -T`, `tail -n 100 /var/log/syslog` | System and service logs |
| **Systemd** | `systemctl status <service>`, `systemctl list-units --failed`, `systemctl show <service>` | Service health |
| **Kernel** | `dmesg -T --level=emerg,alert,crit,err`, `cat /proc/sys/vm/overcommit_memory` | Kernel errors, OOM config |
| **Packages** | `dpkg -l \| grep <pkg>`, `apt list --installed 2>/dev/null \| grep <pkg>` | Installed packages |

### 5.2 Explicitly Blocked Patterns

Any command matching these patterns is **rejected before execution**:

- `rm`, `rmdir`, `unlink`, `shred`
- `mkfs`, `fdisk`, `parted`, `dd`
- `kill`, `killall`, `pkill`
- `reboot`, `shutdown`, `poweroff`, `init`
- `systemctl start`, `systemctl stop`, `systemctl restart`, `systemctl enable`, `systemctl disable`
- `apt install`, `apt remove`, `yum install`, `yum remove`, `pip install`
- `chmod`, `chown`, `chattr`
- `useradd`, `userdel`, `usermod`, `passwd`
- `iptables -A`, `iptables -D`, `iptables -F` (write operations)
- `echo ... >`, `tee`, `sed -i`, `awk -i inplace` (file writes)
- `curl`, `wget`, `nc`, `ncat` (outbound network — except for DNS lookups)
- Any command with `|`, `>`, `>>` redirecting to files outside `/dev/null`
- Backtick or `$(...)` subshell execution within arguments

### 5.3 Command Validation Flow

```
Agent formulates command
        │
        ▼
┌───────────────────┐
│  Regex Blocklist  │──── MATCH ──── REJECT + log reason
│  Check            │
└───────┬───────────┘
        │ PASS
        ▼
┌───────────────────┐
│  Allowlist Prefix │──── NO MATCH ── REJECT + log reason
│  Check            │
└───────┬───────────┘
        │ MATCH
        ▼
┌───────────────────┐
│  Argument         │──── SUSPICIOUS ── REJECT + log reason
│  Sanitization     │
└───────┬───────────┘
        │ CLEAN
        ▼
    EXECUTE via SSH
```

- `az vm create`, `delete`, `start`, `stop`, `restart`, `deallocate`
- Any command with `--output-file`, `>`, `>>` (file writes)

### 6.3 Credential Injection

Cloud CLI commands require credentials. The flow:

```
Agent formulates cloud CLI command
        │
        ▼
Vault Manager retrieves tenant credentials (by provider)
        │
        ▼
Credentials injected as environment variables
into the sandboxed execution context:
  • AWS: AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_DEFAULT_REGION
  • GCP: GOOGLE_APPLICATION_CREDENTIALS (service account JSON path)
  • Azure: AZURE_CLIENT_ID, AZURE_CLIENT_SECRET, AZURE_TENANT_ID
        │
        ▼
Command executed in sandboxed container
        │
        ▼
Credentials purged from environment after execution
```

Credentials are **never** embedded in the command string itself. They are injected exclusively via environment variables and purged after each execution.

## 7. Command Execution Layer (The Hands)

### 7.1 Execution Model

Commands run inside the tenant's sandboxed container (Docker). Since each tenant already has a dedicated container (per main PRD Section 4.2), command execution happens within that same isolation boundary.

```
┌──────────────────────────────────────────────────┐
│              TENANT CONTAINER                     │
│                                                   │
│  ┌──────────────┐    ┌────────────────────────┐  │
│  │  VCE-HQ      │    │  Execution Sandbox     │  │
│  │  Agent       │───▶│                        │  │
│  │  Process     │    │  • Subprocess call     │  │
│  │              │◀───│  • Timeout enforced    │  │
│  │              │    │  • stdout/stderr captured│ │
│  └──────────────┘    │  • Exit code tracked   │  │
│                      └────────────────────────┘  │
│                                                   │
│  ┌──────────────────────────────────────────────┐ │
│  │  For remote hosts: SSH with tenant keys       │ │
│  │  • OS commands → SSH to target host           │ │
│  │  • Cloud CLI → local execution with creds     │ │
│  └──────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────┘
```

### 7.2 Execution Constraints

| Constraint | Value | Rationale |
|---|---|---|
| **Command timeout** | 30 seconds | Prevent hung commands from blocking the pipeline |
| **Max output size** | 64 KB (stdout), 16 KB (stderr) | Prevent memory exhaustion from verbose commands |
| **Max iterations per agent** | 5 | Bound the ReAct loop |
| **Max total commands per session** | 15 | Prevent runaway sessions across agents |
| **Concurrent commands** | 1 (sequential only) | Predictable resource usage |
| **Output truncation** | Tail-truncate if exceeding max | Always capture the most recent output |

### 7.3 Execution Result Schema

```json
{
  "command_id": "uuid",
  "command": "df -hT",
  "agent": "os_engineer",
  "timestamp": "ISO-8601",
  "exit_code": 0,
  "stdout": "Filesystem     Type  Size  Used Avail Use% Mounted on\n...",
  "stderr": "",
  "duration_ms": 245,
  "validated_by": "allowlist_v1",
  "truncated": false
}
```

## 8. Security Review — Extended for Command Audit

The mandatory Security Review (Section 4.4 of the main PRD) is extended to validate the commands that were executed:

### 8.1 Additional Review Responsibilities

| Responsibility | Details |
|---|---|
| **Command audit** | Review every command executed by specialist agents. Flag any that seem unnecessarily broad or could leak sensitive data. |
| **Output sensitivity scan** | Check command outputs for sensitive data (API keys, passwords, tokens) that should be redacted before presenting to the user. |
| **Execution justification** | Validate that each command was reasonably necessary for the diagnosis (prevent LLM from running commands "just in case"). |
| **ADR compliance** | Cross-reference commands against tenant ADRs (e.g., "we never query production databases directly" → flag if agent ran `aws rds describe-db-instances` on prod). |

### 8.2 Security Review Input (Extended)

The Security Review agent now receives:

```
Previous input (unchanged):
  • OS Agent analysis
  • Cloud Agent analysis
  • RAG-retrieved ADRs, past decisions, standards

New input:
  • Full command execution log:
    - Each command executed
    - Why the agent decided to run it (reasoning)
    - The output received
    - Whether it was truncated
  • Total command count and execution time
```

## 10. STM/LTM Extensions

### 10.1 STM — Command Execution Log Table

New table added to the per-tenant SQLite database:

```sql
CREATE TABLE IF NOT EXISTS command_executions (
    command_id       TEXT PRIMARY KEY,
    session_id       TEXT NOT NULL REFERENCES sessions(session_id) ON DELETE CASCADE,
    agent            TEXT NOT NULL,       -- 'os_engineer' | 'cloud_engineer'
    command          TEXT NOT NULL,       -- The executed command string
    reasoning        TEXT NOT NULL,       -- Why the agent chose to run this
    exit_code        INTEGER,
    stdout           TEXT,
    stderr           TEXT,
    duration_ms      INTEGER,
    validated_by     TEXT NOT NULL,       -- 'allowlist_v1'
    truncated        INTEGER DEFAULT 0,  -- boolean
    created_at       TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now'))
);

CREATE INDEX IF NOT EXISTS idx_cmd_exec_session ON command_executions(session_id);
```

### 10.2 LTM — Diagnostic Patterns

When an incident is resolved, the successful diagnostic *pattern* (which commands were useful, what they revealed) is embedded into LTM alongside the resolution. This allows future RAG queries to retrieve not just "what happened" but "how we diagnosed it" — teaching the agent to run the right commands faster next time.

## 13. Success Metrics (Brain Module)

| Metric | Target |
|---|---|
| **Diagnosis accuracy with commands** | ≥ 90% (up from 80% without commands) |
| **Avg commands per session** | ≤ 3 (efficiency — agents should need few commands) |
| **Command rejection rate** | < 1% (agents learn to stay within allowlist) |
| **Time per command execution** | < 5 seconds average |
| **Security Review flag rate on commands** | < 5% (agents should not run unnecessary commands) |
